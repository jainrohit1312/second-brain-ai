# Second Brain — Research Notes

The open questions, the candidate choices, and the experiments that would settle them. This is the working document behind [DECISIONS.md](./DECISIONS.md)'s Proposed ADRs.

Status: draft — scaffold phase. **No measurement has been run.** Every result cell below says `— TBD (measure)` on purpose: this document records the measurement plan and the decision criterion, not a result. Any number that appears here without being attributed to a run of a named experiment is a mistake.

## A note on how these tables are meant to be read

- **`— TBD (measure)`** means the cell is waiting on an experiment, and the experiment is named in the row or the section.
- **A cost column is a _posture_, never a price.** Provider pricing changes and depends on contract terms; quoting a number here would be wrong within a quarter and would create a false basis for the roadmap's cost model. What matters for the decision is whether cost scales with corpus size (one-time, at ingest) or with usage (per query), and whether it is bounded by something we control.
- **A latency column is a shape, never a millisecond.** The question is whether latency is bounded by a round trip or by a generation, and whether it sits in the interactive path or in a background job.
- **The decision column states the criterion before the result exists.** Writing the criterion first is the only thing that prevents a benchmark from being run until it agrees with a preference.

## Embedding models

Embeddings are the single largest lever on retrieval quality and, at ingest, the largest recurring cost. The default is pinned because `pgvector` columns have a fixed width ([ADR-004](./DECISIONS.md#adr-004-pinned-embedding-dimensions-and-a-mandatory-re-embedding-migration)).

### What actually decides it

1. **Recall@8 on the retrieval evaluation set.** Not "MTEB score" — the public benchmarks are not this corpus, and this corpus is one user's reading history. The harness from phase 4 is the instrument, and the metric is whether the correct source appears in the top 8 for a question that a human wrote.
2. **Asymmetry correctness.** `nv-embedqa-e5-v5` is asymmetric. The `embed` edge function takes `inputType` as a **required** parameter for exactly this reason ([API_REFERENCE.md](./API_REFERENCE.md)). The measurement is the recall difference between correct and incorrect `input_type` — if that difference is small, the parameter's strictness is over-engineering; if it is large, it confirms the design.
3. **The re-embed cost of being wrong.** Choosing a model means a full corpus re-embed to change it. So the criterion is not only "which is best", but "how much does the _first_ choice cost to reverse". A model whose width is also offered natively at 1024 is materially cheaper to leave behind.
4. **Whether ingest can be done locally.** A local embedding model changes the privacy story from "content goes to one provider for embedding" to "content stays local for embedding". That is a product-relevant difference, not just a cost one, and it belongs in the comparison.

### The experiment: embedding options (E1, E2)

**E1 — Embedding model comparison.** Build a fixed passage set (a few hundred chunks from real reading, committed as fixtures since the eval corpus must not be a moving target) and a set of 50 questions with known correct sources. For each candidate model: embed the passages once, embed the questions as queries, run the vector leg alone at `RETRIEVAL_TOP_K`, and record recall@1, recall@3, recall@8, and the rank of the first correct result. Repeat for `nv-embedqa-e5-v5` with `input_type` correct and deliberately wrong. **Decision criterion:** the default changes only if a candidate beats the incumbent by a margin that would be visible to a user on the top-3 results, _and_ the corpus-wide re-embed cost is acceptable. A tie goes to the incumbent, because a re-embed is expensive and a new model's failure modes are unknown.

**E2 — Embedding stability.** Embed the same text twice, a week apart. Record the cosine similarity of the pair. This is a cheap test with a real consequence: if the provider's vectors drift for identical input, then `content_hash`-based skip logic is unsound and every row must be re-embedded whenever any drift is suspected.

## LLMs for classification and distillation

Two different tasks with different requirements. Classification is a bounded label choice; distillation is open-ended structured extraction. They should probably not use the same model, and the criteria below are deliberately specific to _structured extraction_ rather than to general chat quality, because that is the failure that costs money and produces wrong memories.

### Criteria that matter _for structured extraction specifically_

1. **JSON reliability is the gating criterion, not reasoning quality.** A model that reasons beautifully and emits one trailing comma produces a retry, and a retry doubles the cost of that document. `LlmProvider.completeJson` normalises the failure mode into a repair loop ([ADR-005](./DECISIONS.md#adr-005-provider-abstraction-behind-a-factory-rather-than-direct-sdk-usage)), but the retry rate is the number that decides.
2. **Whether a native JSON-constrained mode exists.** A provider that can be told "only emit this schema" removes an entire class of failure. A provider without it needs prompt-level coaxing and a repair loop, which is strictly worse for a high-volume background job.
3. **Empty-list honesty.** The critical behaviour for this product is a model that returns `[]` rather than inventing something to be helpful. A model that always finds a memory is failing, and this is the single hardest behaviour to measure because it looks like success (ADR-007).
4. **Cost per 1,000 documents** rather than cost per token. Documents are the unit of work; tokens are the input to a price. The number to record is: average input tokens per document × the corpus's document count, plus output tokens at the observed candidate rate.
5. **Context window against a real document.** A long article's chunks plus the distillation prompt must fit. If they do not, the caller splits the document into windows ([API_REFERENCE.md](./API_REFERENCE.md)) — which changes the prompt's quality, because a windowed distillation cannot see the whole argument.
6. **Determinism/consistency.** Running the same chunk through the distiller twice should produce roughly the same memories. If it does not, the adjudication layer has to dedupe against a moving target and `access_count`-style feedback becomes meaningless.
7. **Latency matters less than it looks — with one exception.** Distillation is a background job, so a slow model is a slow backlog. The exception is intent classification on `/v1/chat`, which sits in the interactive path and should be a different, cheaper model call.

### The experiments

**E3 — Structured-extraction reliability bake-off.** A fixture set of 30 documents (a mix of long-form articles, a transcript, a PDF, a changelog, a product page, and at least five documents that **should yield zero memories**). For each candidate model: run the distillation prompt, validate the output against the `MemoryCandidate` zod schema, and record (a) first-pass schema-validity rate, (b) validity rate after one repair, (c) the count and kind distribution of candidates, and (d) how many of the should-yield-zero documents produced candidates anyway. **Decision criterion:** a model is eligible only if first-pass validity is high and false-positive extraction on the empty documents is near zero. Cost is applied as a tiebreak, not as the primary filter — a cheap model that invents memories is more expensive than an expensive one that does not.

**E4 — Distillation adjudication threshold.** Once candidates exist, they must be compared against existing memories. Measure the embedding-similarity distribution between (a) true duplicates, (b) contradictions, and (c) genuinely distinct memories. The deliverable is a threshold pair (merge-above, insert-below) with an explicit ambiguous band that routes to `candidate` status for review. **Decision criterion:** a threshold is acceptable if it produces fewer wrong merges than wrong inserts — a wrongly merged memory loses information and is invisible, while a wrongly inserted one is merely redundant and visible in review.

## What "a memory" should mean

This is the central product question ([PROJECT_OVERVIEW.md](./PROJECT_OVERVIEW.md), ADR-007), and it cannot be answered by a definition alone. It needs worked examples, because two reasonable reviewers will disagree about "is this durable?" and the disagreement is the specification.

The rules:

- A **memory** is a durable, self-contained statement about the user or their work.
- A **summary** is a restatement of a document. It is not a memory. `documents.summary` exists for display and is not retrievable.
- A **chunk** is what was read. It is not a memory either, but it is retrievable.
- **Zero memories is a valid outcome** for a document, and the eval must include documents that should produce none.

### Example 1 — A technical blog post about Postgres index types

**Should produce**

| Kind        | Statement                                                                                                                                                      | Why it qualifies                                                                                                                                       |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `insight`   | "HNSW's incremental build is the reason it was chosen over IVFFlat for the retrieval service's vector indexes, because the corpus grows a document at a time." | Connects a fact from the article to a decision the user actually made. Self-contained, and it would be useful in six months.                           |
| `reference` | "The pgvector operator for cosine distance is `<=>`."                                                                                                          | A durable fact the user will look up again. Low importance, but retrieval-valuable because it is exactly the kind of thing a paraphrase search misses. |

**Should not produce**

| Candidate                                                        | Why not                                                                                          |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| "This article explains the difference between IVFFlat and HNSW." | A summary. It is about the article, not the user, and it answers no question the user would ask. |
| "The article mentions that index build time matters."            | A fragment, not a proposition. No subject, no conclusion, not self-contained.                    |
| "Postgres has several index types."                              | True, durable, and useless. It has no relationship to anything the user is doing.                |

### Example 2 — A meeting notes page about a client project

**Should produce**

| Kind       | Statement                                                                              | Why it qualifies                                                                                                         |
| ---------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `decision` | "The Northwind migration was deferred to Q1 because Northwind's legal review slipped." | A decision with a reason. Exactly the kind of thing that is asked about later and impossible to find in a notes archive. |
| `project`  | "Northwind is a client project currently in schema-migration planning."                | Establishes an entity that later queries will reference by name.                                                         |
| `task`     | "Confirm the Q1 migration window with Northwind before the end of September."          | An obligation with a deadline. Observable when completed, and therefore supersedable.                                    |

**Should not produce**

| Candidate                                | Why not                                                                                                                                                                                         |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "The meeting covered four agenda items." | A summary of the meeting's shape. Useless a week later.                                                                                                                                         |
| "Priya attended the meeting."            | True, durable, and not a memory about the _user's_ work — it is an attendance record. If Priya becomes an `entity` memory it should be because she owns something, not because she was present. |
| "The team discussed the migration."      | An activity description with no proposition. Durable, in the sense that it is still true, but it answers nothing.                                                                               |

### Example 3 — A long-form essay the user skimmed

**Should produce**

Possibly nothing — and that is the correct answer in the case where the user skimmed it, retained nothing, and made no decision. This is the most important of the three examples, because it is the case a metric optimising for "memories per document" gets wrong.

**Should produce, if the user did engage**

| Kind         | Statement                                                                                                                                       | Why it qualifies                                                                                                         |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `preference` | "The user prefers explicit error taxonomies over generic error types when reviewing a service's error handling."                                | Derived from behaviour, not from the article's content. Durable, and it changes how future suggestions should be framed. |
| `insight`    | "The essay's argument that retrieval quality is bounded by chunk boundaries is relevant to the chunking-strategy decision deferred to phase 7." | Connects an external argument to an open decision in the user's own project.                                             |

**Should not produce**

| Candidate                                                                   | Why not                                                                                                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A synopsis of the essay.                                                    | A summary.                                                                                                                                                                                                                                                                                                                                                 |
| Any `fact` about the essay's subject matter with no connection to the user. | This is the most likely over-extraction failure: the model extracts the article's content as if the user had asserted it. A memory is about the user's beliefs and work, not about things the user read. Distinguishing "the user read that X is true" from "the user believes X" is the hardest part of the prompt, and it should be measured explicitly. |

### What these examples imply for the schema and the eval

- **`kind: 'insight'` and `kind: 'decision'` are the highest-value kinds** and the ones that most require cross-referencing the user's existing memories. A distiller that only produces `fact` and `reference` is a glossary, not a memory system.
- **The should-not-produce lists are as much a part of the fixture as the should-produce lists.** The evaluation harness asserts both directions, and a document that produces a candidate on its should-not list is a failure even if it also produced the right ones.
- **The "user believes X vs user read X" distinction needs a named negative example** in the fixture set, and it is currently the least well specified behaviour in the whole system. It is the leading candidate for the first prompt-engineering work in phase 3.

The measurement that matters here is not a success rate on a test set of URLs — it is the **distribution of `extraction_status` across the user's actual capture stream**, which is the first thing the activity dashboard should surface. A user who discovers that 30% of their reading produced no memories needs to know why, per document.

## Chunking strategy comparison

The v1 decision is recursive splitting with semantic chunking deferred ([ADR-013](./DECISIONS.md#adr-013-proposed-recursive-chunking-in-v1-semantic-chunking-deferred-to-phase-7)). The comparison below is what phase 7 evaluates.

| Strategy      | Boundary rule                                                                   | Cost at ingest                          | Determinism                                          | Strength                                                                                  | Weakness                                                                                                                                            | Where it will be tested                         |
| ------------- | ------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `fixed`       | Every N tokens                                                                  | Zero                                    | Deterministic                                        | Trivial; a useful control condition                                                       | Cuts mid-sentence and mid-argument; produces chunks that are bad for both embedding and citation                                                    | Control only — expected to lose                 |
| `recursive`   | Heading → paragraph → sentence → hard cut, with overlap                         | Zero (no model calls)                   | Deterministic                                        | Respects document structure; yields `heading_path` for free; works with the provider down | Degenerates on unstructured text (transcripts); long sections still cut arbitrarily                                                                 | **v1 default.** Baseline for phase 7            |
| `semantic`    | Embed sentences, cut where adjacent-sentence similarity drops below a threshold | One embedding call per sentence         | **Nondeterministic** unless frozen by `content_hash` | Coherent chunks across topic shifts; the case it wins is the case recursive loses         | Cost scales with sentence count; the threshold needs tuning; a retry can produce different chunks                                                   | Phase 7, against the recursive baseline         |
| Late chunking | Embed the whole document, pool token embeddings per chunk                       | One long-context embedding per document | Deterministic per model                              | Each chunk embedding carries whole-document context — helps pronoun-heavy documents       | Needs a long-context embedding model and a pooling implementation; not expressible in the current `EmbeddingProvider` interface without widening it | Phase 7 spike; interface impact to assess first |

**Metrics for the comparison.** (a) recall@8 in the retrieval harness, (b) citation snippet quality — whether a returned snippet is intelligible without its neighbours, judged by a human on a sample, (c) ingest cost per document, (d) ingest wall-clock per document, (e) chunk-count inflation, which affects index size and near-duplicate retrieval hits.

**The decision criterion, stated in advance.** Semantic chunking replaces recursive in a document's pipeline only if it improves recall@8 by a margin a user would notice, on the document classes it is claimed to help (transcripts, long unstructured essays), and the ingest cost increase is acceptable for those classes specifically. **A class-specific strategy is a legitimate outcome**: `strategy` is a column, and using `semantic` only for transcripts is a smaller, better-justified change than a corpus-wide switch. That possibility is the main reason `ChunkingStrategy` has three values rather than one.

## Reranking options

The decision is Proposed in [ADR-014](./DECISIONS.md#adr-014-proposed-local-reranker-rather-than-a-hosted-reranking-api). The comparison that settles it:

| Option                                            | Added latency                            | Cost posture                    | What leaves the service                            | Ops artifact                                                                | Quality expectation                               |
| ------------------------------------------------- | ---------------------------------------- | ------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------- |
| **Local cross-encoder** (ONNX or a local runtime) | CPU-bound; scales with `RETRIEVAL_TOP_K` | Fixed compute; no per-query fee | **Nothing**                                        | A model file to obtain, version, ship, and warm; memory for the working set | Below the best hosted reranker; `— TBD (measure)` |
| **Hosted reranking API**                          | One network round trip                   | Per query                       | **The user's question and the candidate passages** | None                                                                        | Best available; `— TBD (measure)`                 |
| **No reranking** (current degrade path)           | Zero                                     | Zero                            | Nothing                                            | None                                                                        | RRF order; the baseline the other two must beat   |

**The privacy axis, which is the real argument.** Embeddings and distillation already send content to a provider, so reranking does not introduce content egress. It introduces _question_ egress: the user's raw, unredacted, actively-intended query, which is a different kind of artifact from an article they happened to scroll past. That is why the proposal favours local, and it is also why the hosted option stays implemented behind the interface rather than being rejected — a user who values ranking quality over that distinction should be able to choose.

**What must be measured (E5).**

1. **Quality delta vs. no reranking.** Recall@3 and nDCG over the retrieval eval set, with and without. If the delta is small, the honest conclusion is to skip reranking entirely and keep the degrade path as the only path — which would be a cheaper and simpler system.
2. **Local vs. hosted delta.** The same metric set for both implementations. This is the number that decides ADR-014, weighed against the privacy axis.
3. **Latency on the retrieval service's actual host**, with the database doing concurrent work. A reranker benchmarked on an idle machine is not a useful number, because the retrieval service and Postgres share CPU.
4. **Cold-start cost.** The first query after idle with a local reranker. If it is seconds, the service needs a warm-up strategy, and that is a real operational cost of the local option.
5. **Licence terms of any shipped model artifact.** Redistribution is a licensing act, and this must be verified before adoption rather than after.
6. **Whether exact-identifier queries are actually harmed by reranking.** The design routes them around it ([ADR-014](./DECISIONS.md#adr-014-proposed-local-reranker-rather-than-a-hosted-reranking-api)); the measurement is whether that routing is necessary or merely cautious.

## The importance-scoring cold start

`ImportanceSignals` has fourteen keys ([DECISIONS.md](./DECISIONS.md#adr-009-client-side-pre-scoring-and-server-side-re-scoring-with-the-client-score-untrusted)). On a brand-new install, three of them are structurally unavailable, and they are among the most valuable:

| Signal                                                       | Available at cold start                                                                       | Why not                                                                                                                                             |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `topicNovelty`                                               | **No**, until the corpus has topics                                                           | It is defined relative to what the user already knows. With no corpus there is nothing to be novel relative to.                                     |
| `revisitCount`                                               | **No**, until history exists                                                                  | A first visit is a first visit.                                                                                                                     |
| `isUniqueDomain`                                             | **Degenerate** — every domain is unique on day one                                            | The signal is `true` for everything, which makes it uninformative and, worse, makes a naive rubric score _everything_ as more important than it is. |
| `hasSelection` / `hasCopy` / `isBookmarked` / `isDownloaded` | Yes                                                                                           | Directly observed on the event.                                                                                                                     |
| `dwellSeconds` / `scrollDepthPct` / `wordCount`              | Yes                                                                                           | Directly observed.                                                                                                                                  |
| `youtubeWatchedPct`                                          | Yes                                                                                           | Directly observed.                                                                                                                                  |
| `isWorkingHours`                                             | Yes, and it is the only context signal that works on day one                                  | Pure clock arithmetic.                                                                                                                              |
| `appIsExcluded`                                              | Always `false` at capture, by construction; meaningful only on a re-score after a rule change | ADR-009                                                                                                                                             |

### Why this is a problem and not a footnote

The client-side pre-score is a **filter**, not a ranking (ADR-009), and it applies only to `PASSIVE_EVENT_TYPES` (`page_view`, `page_read`, `youtube_watch`, `app_session`). `EXPLICIT_INTENT_EVENT_TYPES` — `selection`, `copy`, `search`, `bookmark`, `download` — bypass the threshold entirely, because a deliberate user action is not something a heuristic gets to discard. That narrows the blast radius of the cold start but does not remove it: the passive types are the highest-volume capture, and a page the user read carefully for twenty minutes is exactly a `page_read`.

An event below `IMPORTANCE_MIN_THRESHOLD` (which mirrors `IMPORTANCE_BAND_THRESHOLDS.low`, i.e. `0.25`) is never uploaded, and the loss is **irrecoverable**. So a cold-start rubric that under-scores loses real data on the first day, exactly when the user is evaluating whether the product works — which is the worst possible time to lose their first article.

The opposite failure is cheaper but still real: a rubric that over-scores on day one uploads noise, pays to embed it, and may distil spurious memories from it. Note that the distillation gate (`DISTILLATION_MIN_BAND = 'normal'`, i.e. `0.45`) bounds the second half of that cost independently: noise that gets uploaded still has to clear a higher bar before it consumes a distillation call.

### Candidate approaches

| Approach                                  | Mechanism                                                                                                                             | Cost                                                                     | Risk                                                                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Cold-start rubric**                     | A second, more permissive rubric while `revisitCount`/`topicNovelty` are unavailable, keyed on observed signals plus `isWorkingHours` | One extra rubric to maintain, and a discontinuity when it switches       | Two rubrics that must be kept in step; the switch point becomes a thing to get wrong                                                    |
| **Degenerate-signal suppression**         | Treat an unavailable signal as _absent_ rather than as `true`, and renormalise the weights over the available signals                 | A renormalisation step in the scorer; the sum of weights changes meaning | Renormalising changes the effective weight of the available signals, so the threshold's meaning shifts                                  |
| **Bootstrap mode with a lower threshold** | For the first N days or first N events, hold `IMPORTANCE_MIN_THRESHOLD` at a lower value per device                                   | More upload on day one; more post-hoc deletion needed                    | The user's first impression of the system is more content than they expected — arguably good, arguably noisy                            |
| **Nothing — accept the cold start**       | No special handling; the day-one rubric is slightly worse                                                                             | None                                                                     | Silent, irrecoverable data loss at the moment of first evaluation. **This is the option the measurement exists to rule out or accept.** |

The honest candidate is a combination: suppress degenerate signals rather than treating them as `true` (which fixes the _wrong_ direction of error), and lower the threshold slightly during bootstrap (which fixes the other). The decision needs a number, not an argument.

### The experiment: cold-start simulation (E6, E7)

**E6 — Day-one simulation.** Replay a fixture corpus as if it were a fresh install: seed nothing, then feed events in chronological order, computing the importance score at each step with the real rubric. Record (a) how many events fall below the threshold, (b) of the events that _would_ have been kept once history existed, how many were dropped during the cold window, and (c) the aggregate score of dropped events versus the corpus's eventual scoring. **Decision criterion:** the cold-start drop rate of eventually-important events must fall below a stated bound (a percentage chosen before the run), or a bootstrap mechanism is required. The measurement's _shape_ is more important than its number: "which signals are structurally unavailable, and what does that do to the filter" is a question the eval can answer definitively.

**E7 — Threshold calibration.** Run the same replay with `IMPORTANCE_MIN_THRESHOLD` at several values and record retained-event count, retained-event importance distribution, and the false-drop rate. **Decision criterion:** pick the lowest threshold whose retained volume is affordable for embedding and distillation, on the principle that a dropped event is unrecoverable while an uploaded one is merely costly. This tunes a constant that otherwise stays at a guess.
